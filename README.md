# Мониторинг цен: МОНОЛИТ РУС vs ВсеИнструменты

Система ежедневного автоматического сравнения цен и наличия товаров поставщика
**МОНОЛИТ РУС** (бренды LEIYA, Monolit MO-L, инструмент Monolit) с публичными ценами
маркетплейса **ВсеИнструменты** (vseinstrumenti.ru, базовая розница Москвы).

Каждый день система заходит на сайт ВсеИнструменты, снимает актуальные цены, наличие
и сроки поставки, сравнивает их с ценами поставщика, формирует Excel-отчёт с тремя
листами (сравнение, сводный индекс с графиками, история замеров) и рассылает его по
электронной почте в виде красивого HTML-письма. Все замеры копятся в истории, поэтому
со временем виден тренд: по каким позициям стало выгоднее, по каким — хуже.

---

## Что делает система (коротко)

1. **Собирает данные ВсеИнструменты** — цены, наличие, срок поставки по товарам
   брендов LEIYA, Monolit MO-L и инструменту Monolit.
2. **Сравнивает с ценами поставщика** МОНОЛИТ РУС — считает разницу в процентах,
   сводные коэффициенты (индекс наличия, доля «в наличии» / «нет в наличии»,
   средний срок, средняя разница цены).
3. **Ведёт историю замеров** — каждый прогон добавляет новый снимок, поэтому видна
   динамика по каждому коду товара (цена снизилась/выросла, срок сократился/вырос,
   товар появился/пропал).
4. **Формирует Excel-отчёт** из трёх листов.
5. **Рассылает отчёт письмом** с вложением на список получателей, копия письма
   сохраняется в папку «Отправленные» ящика-отправителя.
6. **Предупреждает о капче** — если сайт запросил проверку, прогон не портит данные,
   а присылает оповещение в личку Telegram, чтобы человек прошёл проверку вручную.

## Как работает скрейпинг (важная особенность)

Скрейпинг идёт **через уже открытый в рабочей машине Chrome** по протоколу
отладки (CDP, `http://localhost:9222`), а не через «чистый» автоматический браузер.
Это осознанное решение: ВсеИнструменты защищены Servicepipe, а в живой сессии
реального браузера с куками, где человек один раз прошёл проверку, каталог
отдаётся нормально.

### Почему капча появлялась постоянно

Servicepipe проверяет **каждый новый документ** (навигацию). Старый код на каждый
URL делал `page.goto()` в новой вкладке — то есть 6 раз за прогон заново запускал
JS-challenge. После того как человек проходил капчу, следующая же навигация скрипта
снова попадала под подозрение, и капча возвращалась.

Теперь страницы забираются **обычным `fetch()` изнутри одной уже прогретой вкладки**:

```python
data = await page.evaluate(FETCH_JS, {"url": url, "timeout": 45000})
```

Для сайта это запрос фронтенда (как подгрузка каталога), а не переход на новую
страницу, поэтому:
- clearance-куки переиспользуются;
- JS-challenge не перезапускается;
- HTML сразу парсится `DOMParser`'ом в браузере, наружу уходит только готовый JSON
  (код, название, цена, наличие, ссылка).

Если вкладки на сайте ещё нет, она один раз открывается на главной — это
единственная навигация за прогон.

### Поведение при защите

Состояние определяется в `captcha.py` (функция `classify_page`) по DOM, а не по
слову «проверка» в тексте (из-за него раньше были ложные срабатывания):

| Состояние | Признак | Что делает прогон |
|-----------|---------|-------------------|
| `ok` | есть плитки `[data-qa="products-tile"]` | продолжает сбор |
| `challenge` | тег `<js-challenge-loader>` | ждёт до 45–60 с, обычно проходит сам |
| `captcha` | виден `#id_captcha_frame_div` / iframe Servicepipe | см. ниже |
| `blocked` | HTTP 403 или текст «доступ ограничен» | пробует открыть документом; при повторе — выход `2` |

### Капча: человек в контуре, без остановки прогона

При капче прогон:
1. делает скриншот капчи и сохраняет HTML в `captcha/` рабочей папки;
2. присылает **фото капчи в Telegram**;
3. ждёт до `MONO_CAPTCHA_WAIT_MIN` минут (по умолчанию 20), опрашивая страницу;
4. человек может либо пройти капчу в Chrome (VNC), либо **ответить на сообщение
   бота кодом с картинки** — бот введёт его в поле и отправит форму;
5. как только проверка пройдена — прогон **продолжается с того же места**,
   перезапускать ничего не нужно;
6. если время вышло — данные не перезаписываются, выход `2`.

Важно: картинка не распознаётся автоматически. Это осознанно — капча Servicepipe
динамическая, OCR даёт много ошибок, а главная причина её появления (навигация на
каждую страницу) уже устранена.

Сканируемые разделы ВИ заданы константами в начале `daily_run.py`
(`LEIYA_PAGES`, `MOL_PAGES`, `MONO_PAGES`).

Коды выхода `daily_run.py`:
- `0` — успех (отчёт пересобран и разослан);
- `2` — капча/блокировка (данные сохранены, прислано Telegram-оповещение);
- `1` — иная ошибка (ошибка сборки/исключение).

### Диагностика

```bash
python captcha_debug.py                       # проверить главную страницу бренда
python captcha_debug.py "<URL>"               # проверить конкретную страницу
python daily_run.py --check                   # только проверить доступ и собрать 1 страницу
python daily_run.py --wait-captcha 0          # не ждать человека (старое поведение)
```

## Структура Excel-отчёта (3 листа)

1. **«Сравнение цен»** — все позиции (LEIYA + MO-L + инструмент Monolit) с ценой
   поставщика и ценой ВИ, разницей в %, наличием, сроком поставки, динамикой
   относительно прошлого замера и ссылкой на карточку ВИ.
2. **«Сводный индекс»** — агрегированные коэффициенты и графики динамики
   («средняя температура по больнице»): индекс наличия, доли «в наличии» / «нет»,
   средний срок, средняя разница цены vs ВИ.
3. **«История замеров»** — все снимки по датам, основа графиков.

**Пометка «проверить ед. изм.»** — часть позиций инструмента Monolit помечаются
флагом, когда цена поставщика может быть указана за штуку из упаковки, а ВИ продаёт
поштучно (или наоборот). Такие строки требуют ручной сверки единицы измерения.

## Рассылка письма

`send_report.py` отправляет отчёт **по SMTP с реального ящика-отправителя**
(`smtp.mail.ru`, SSL 465, с откатом на STARTTLS 587). Письмо уходит «от нас»,
поэтому не попадает в спам Gmail (в отличие от служебного домена платформы).

Тело письма — **красивое HTML** с шапкой-баннером, таблицей сводного индекса
(цветные стрелки ▲/▼ и значение «было»), цветной плашкой вердикта и списками
изменившихся позиций. Данные для письма берутся из `summary.json`.

**Копия в «Отправленные».** Через «чистый» SMTP отправленные письма в папку
«Отправленные» не попадают — это делает протокол IMAP. Поэтому после каждой
успешной отправки `send_report.py` кладёт точную копию письма (с вложением) в папку
«Отправленные» ящика-отправителя через `IMAP APPEND` (`imap.mail.ru:993`). Папка
определяется автоматически (по флагу `\Sent`, иначе по имени «Отправленные»/«Sent»).
Если IMAP недоступен — письмо всё равно уходит получателям, просто копия не
сохраняется (пишется строка в лог).

Список получателей задаётся константой `RECIPIENTS` в начале `send_report.py`.

## Секреты (не хранятся в коде)

Весь код читает учётные данные из JSON-хранилища
`/home/ubuntu/.config/abacusai_auth_secrets.json`. **В репозиторий этот файл не
попадает.** Формат и имена ключей — см. `secrets.example.json`.

Нужны два блока:

**`mailrusmtp`** — почта-отправитель (Mail.ru):
- `smtp_host` — обычно `smtp.mail.ru`
- `smtp_user` — адрес ящика-отправителя
- `smtp_password` — пароль приложения для SMTP
- `imap_host` — обычно `imap.mail.ru` (необязателен, по умолчанию `imap.mail.ru`)
- `imap_password` — пароль приложения **с доступом по IMAP** (для копии в «Отправленные»)

> Mail.ru требует отдельные **пароли для внешних приложений** (Настройки →
> Безопасность). Для IMAP может понадобиться отдельный пароль с доступом к IMAP.

**`telegram`** — бот для оповещений о капче:
- `bot_token` — токен Telegram-бота
- `chat_id` — id чата (личка), куда слать оповещение

## Установка и запуск

```bash
# 1. Зависимости
pip install -r requirements.txt
#    Playwright используется только как CDP-клиент к системному Chrome,
#    поэтому `playwright install chromium` не нужен.

# 2. Секреты
#    Создать /home/ubuntu/.config/abacusai_auth_secrets.json
#    по образцу secrets.example.json (с реальными значениями).

# 3. Живая сессия Chrome с открытым портом отладки (для скрейпинга ВИ),
#    где капча уже пройдена человеком:
#    google-chrome --remote-debugging-port=9222 ...

# 4. Разовый прогон
python3 daily_run.py        # полный цикл: сбор → сборка → рассылка
# либо по шагам:
python3 daily_run.py --check   # проверить доступ и собрать одну страницу
python3 build_report.py        # пересобрать Excel из уже собранных данных
python3 send_report.py         # разослать готовый отчёт

# 5. Тесты распознавания защиты (браузер не нужен)
python -m unittest discover -s tests -v
```

Пути по умолчанию — серверные (`/home/ubuntu/monolit_vi_report`, `/home/ubuntu/tmp`).
На другой машине их можно не править в коде, а задать переменными окружения:
`MONO_REP`, `MONO_TMP`, `MONO_XLSX`, `MONO_SECRETS`, `MONO_CDP_PORT`,
`MONO_CHROME_PROFILE`, `MONO_CAPTCHA_WAIT_MIN`. На Windows значения по умолчанию
берутся из профиля пользователя (`~/monolit_vi_report` и `%TEMP%`).

## Расписание

Прогон рассчитан на ежедневный запуск планировщиком в **08:00 по Москве**
(`Europe/Moscow`). Запускается `daily_run.py`; при коде выхода `2` (капча) и при иных
нештатных кодах оповещение идёт в Telegram-личку, по email о сбоях не пишется —
только штатный отчёт при успешном прогоне.

Пример записи cron (сервер в UTC, 08:00 МСК = 05:00 UTC):

```cron
0 5 * * *  cd /home/ubuntu/monolit_vi_report && /usr/bin/python3 daily_run.py >> daily_run.log 2>&1
```

## Примечания по точности данных

- Цены и наличие ВИ — **базовая розница Москвы**; по регионам и с промокодами могут
  отличаться.
- Позиции с пометкой «проверить ед. изм.» требуют ручной сверки единицы измерения
  (упаковка vs штука).
- Отчёт формируется автоматически; первый замер — базовая точка отсчёта, динамика
  появляется со второго прогона.
